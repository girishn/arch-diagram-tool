# Spec schema v1 — draft for confirmation

Types: `src/schema.ts`. Validator: `src/validate.ts` (no dependencies). Both are drafts until confirmed.

## Shape

```
DiagramSpec { version: 1, title, description?, nodes[], links[], zones?[], trace?[], prose?[], lenses?[] }
```

- **node**: `id, label, sub?, at {col,row}, icons[], scale?, peripheral?, detail? {tag, role, why, tradeoff}, lenses? {<lensId>: {badge, text?, level?}}`
- **link**: `from, to, label, detail?, via?, labelAt?, offPath?, pattern?, interaction?, protocol?, twoWay?, traffic?, lenses? {<lensId>: {badge, text?, level?}}`, plus optional `mentions`
- **zone**: `id, label, kind?, members?[], parent?, bounds? {c0,r0,c1,r1}`
- **prose block**: `id, text, mentions[]` (spec-level `prose?`), plus optional `mentions` on node `detail` and on links
- **trace step**: `node, label`
- **lens**: `id, label?, summary?` (label is optional when the id is a preset) (Flow is built in; Security and Cost become ordinary declared lenses)

## The contract (what a generator can rely on)

**Optional data on nodes, links and zones.** None of it changes the picture; the text view shows it for nodes.

- `tags: string[]`, `properties: { key: string | number | boolean }`, `references: [{ label, url }]` (runbooks, ADRs, dashboards, code), `source: { address?, file?, line? }` (for example a Terraform address and file and line).
- Links may also carry `id`, unique among links, for tools that refer to a link across edits.
- A reference `url` must be `http(s)`, `mailto`, or a path on the same site (`/x`, `./x`, `../x`, `#x`). `javascript:`, `data:` and protocol-relative `//host` are errors.
- Spec-level `$schema` is allowed (editors use it; the renderer ignores it).

**Your own data.** Any field whose name starts with `x-` is kept and never interpreted or warned about, at every level (spec, node, link, zone). Any other unknown field is a warning that names its path, so a typo such as `ofPath` is caught instead of silently ignored.

**Compatibility rules for v1.**
- Adding an optional field, a new enum value the renderer can fall back from, a new lint warning, or a new lens preset is **not** breaking.
- Removing or renaming a field, making an optional field required, changing what a field means, turning a warning into an error, or removing an enum value **is** breaking and needs `version: 2`.
- Consumers should accept specs with fields they do not know, and show the warnings. This tool does so for fields; a value it does not know for `pattern`, `traffic`, `level` or zone `kind` is still an error today.
- `tests/fixtures/golden/*.json` are specs that were valid when v1 was written and must validate with no errors and no warnings. Add a fixture when v1 gains a field. Never edit one to make a test pass.

## Lint rules, suppressions, the CLI and the JSON Schema

**Rules have stable ids.** Every issue carries a `rule` (for example `trace-unvisited-node`, `link-unknown-node`). The registry is `RULES` in `src/rules.ts`: id, severity and a one-line meaning. An id never changes meaning and is never reused. Errors make a spec unsafe to render; warnings flag gaps.

**`lintIgnore`** (spec level) accepts a warning on purpose:

```json
"lintIgnore": [{ "rule": "trace-unvisited-node", "path": "nodes.registry", "reason": "The registry is a dependency, not part of the request path." }]
```

- `reason` is required, so a suppression is a decision someone can read later.
- `path` is optional and must match the issue's path exactly; without it the rule is silenced everywhere.
- Only warnings can be silenced. An entry with no reason is an error; one naming an unknown rule or an error rule, or one that matched nothing, is a warning, so suppressions cannot go stale.
- Suppressed warnings are not shown but are counted, and SARIF output records them with their justification.

**The CLI** (Node 24 or later, no build step): `node scripts/lint.ts [--format text|sarif|github] [--max-warnings N] <file.json | directory>...`. Exit 0 when there are no errors and no more warnings than `--max-warnings`, 1 otherwise, 2 for a usage, read or parse problem. `--format github` prints workflow commands that become annotations on a CI run; `--format sarif` prints SARIF 2.1.0 for code-scanning tools. `npm run lint:specs` lints `examples/`. Locations are logical (`/nodes/2/detail`, `/nodes/api`), not line numbers.

**The JSON Schema** is `schema/diagram-spec.v1.schema.json` (2020-12), generated by `npm run gen:schema` from the enum lists in `src/schema.ts` and the validator's field lists, and a test fails if the committed file is stale. Point an editor at it with `"$schema": "<path or url>"` for completion and squiggles. It flags unknown fields (the validator only warns) and cannot check semantic rules such as links pointing at real nodes; the validator is the authority. Every example and golden fixture must pass both.

## Decisions to confirm

1. **One node list, not two.** The portfolio's original code splits layout (`DIAGRAM_NODES`) from explanation (`NODES`) and joins them by id. That split is how components lost detail on the portfolio page (open issue 4). Here a node carries both, and `detail` missing is a lint warning.
2. **Lenses are data.** The seed hard-codes `sec` / `cost` fields and a three-value `Lens` type. Here a spec declares lenses and each node supplies a short `badge` plus optional long `text` per lens. A lens may also carry a `summary`, shown in the info strip when that lens is active and nothing is hovered. Trade-off stays in `detail` and shows under Flow.
3. **Icons are opaque keys.** The seed's `tile: "service" | "glyph"` is a property of the icon file, so it moves into the icon pack, not the spec. The spec never names a vendor, which keeps AWS assets out of the public package.
4. **`at` replaces flat `col`/`row`**, and zones are defined by membership (see below) instead of hand-set coordinates.
5. **Trace references nodes only.** Routes between steps come from the link graph (as the renderer does today), and the validator errors if consecutive steps are unreachable.
6. **No Zod/Ajv.** A hand-written validator keeps the "no heavy dependencies" rule. A JSON Schema file can be generated later for editor support.

## Link semantics

- **`pattern`** (default `request-response`): `request-response` (HTTP, gRPC unary, SQL, polling), `event` (webhooks, pub/sub, cron triggers), `message` (queues, commands), `stream` (Kafka, Kinesis, websockets, SSE, replication), `batch` (ETL, backups, file drops), `dependency` (IAM trust, deploy, config, monitoring: no runtime data).
- **`interaction`**: `sync` or `async`. Default is `sync` for request-response and `async` for every other pattern, so it only needs setting for exceptions (async request-reply, a synchronous wait on a queue). Ignored for `dependency`.
- **`protocol`**: free text, shown in the info strip.
- **`twoWay`**: the response returns on the same cable; both ends get an arrowhead.
- **Who initiates.** `from` is the side that starts the call, and `to` is the side that is called. A `twoWay` link means the response comes back on the same path. So Prometheus scraping an app is `from: prometheus, to: app`, `twoWay: true`, not the other way round. Peripherals worked through:

  | Relationship | from → to | pattern | notes |
  | --- | --- | --- | --- |
  | Metrics scrape (pull) | prometheus → app | `request-response`, `twoWay`, `async` | the scraper initiates |
  | Dashboard query | grafana → prometheus | `request-response`, `twoWay` | |
  | Alert routing | prometheus → alertmanager | `event` | |
  | Logs or traces shipped out (push) | app → log store | `stream` | the app initiates |
  | Deploy | pipeline → app | `dependency` | no runtime data; exempt from the traffic lint |
  | Commit trigger | repo → pipeline | `event` | webhook |

  Mark tooling links `offPath: true` so they read as peripheral.
- **`traffic`**: `ingress`, `egress` or `internal`. Shown as an IN / OUT tag on the arrow and in the legend. A link that crosses the edge of a `vpc` or `boundary` zone should be tagged; the validator warns when it is not, and when the tag disagrees with the direction it crosses. Cloud, subnet and other zone kinds are not checked.
- **`offPath`**: the link is not on the main request path (replaces the seed's `dashed`). Independent of `interaction`: an async link can be on the path, and a sync one can be off it.
- **`lenses`**: per-lens `badge` (replaces the label chip while the lens is active) and `text` (info strip), like nodes.
- The spec stays semantic. The renderer picks the visual encoding (line style, arrowheads, a legend), so the list is kept short so that encoding stays predictable.

## Fleets and groupings

- **`scale`** on a node: `{ min, max, unit?, trigger? }`. The card stands for a fleet (auto scaling group, ECS tasks, read replicas, Lambda concurrency) and is drawn stacked with a count badge, never as N separate nodes. `min` may be 0 (scale to zero).
- **Zones** group nodes: `members` lists the nodes directly inside, `parent` nests a zone in another (VPC > subnet, cloud > account), and a parent grows to contain its children. The renderer takes bounds from `resolveZones(spec)`: the tight extent of the members and child zones, padded 0.42 cell for a leaf plus 0.09 per nesting level below, so parents sit outside children. Explicit `bounds` still override.
- A node belongs to one zone only (its innermost); list it there and not in the parents.
- **`kind`** is one of `cloud`, `account`, `region`, `az`, `vpc`, `subnet`, `cluster`, `scaling-group`, `boundary`, `group` (default, neutral).
- Not modelled, by design: per-instance drawing, autoscaling simulation, and a node drawn once per AZ or region. Say "spread across 3 AZs" in the Reliability lens text. Primary/replica is two nodes joined by a `stream` link. A Terraform generator would collapse real resources into these logical nodes and groups.

## Spacing

Grid cells are a base spacing, not a fixed one. Two cards side by side get a wider gap when their arrow's label chip, or their name plates and sub-labels, need it: the chip is placed with the arrowhead and flow still showing 24 px either side, and the plates never touch. Arrows with `via` or `labelAt` are not stretched for. Chips also steer clear of each other, so two links with the same label do not stack. Widths are estimated from the text, using the link's `label` (not a lens badge, which can be longer), so a very long lens badge can still cover more of its cable.

## Peripherals

CI/CD, observability and alerting sit around the system rather than in it. Mark those nodes `peripheral: true` and group them in a zone of kind `tooling`.

- The renderer draws them lighter with a dashed outline, adds a **Tooling** toggle to the toolbar (on by default), and a legend entry. Switching it off removes the peripheral nodes, every link touching them, and any zone left with nothing in it, then lays the rest out again: the plane, the zones and the zoom fit all shrink to what remains, so the core diagram is drawn larger. Hiding a selected tooling node clears the selection. `withoutPeripherals(spec)` returns that reduced spec, itself a valid spec.
- The "never visited by the trace" lint skips peripherals, since tooling rarely sits on the request path. Orphan, missing-detail and prose-mention lints still apply.
- Generic icon keys for tooling: `pipeline`, `repo`, `dashboard`, `alert`, `logs`, `monitor`, with aliases for common tools (Prometheus, Grafana, Alertmanager, Loki, Jenkins, GitHub Actions, ArgoCD, Git and similar). The aliases only pick a generic shape; no vendor marks are drawn.

## Levels and lens presets

- **`level`** on a lens fact (nodes and links): `good`, `info` (default), `warn` or `risk`. The renderer colours the badge and pairs it with an icon or text so colour is never the only signal.
- **Presets** (`src/presets.ts`): list a lens by id alone, e.g. `{ "id": "reliability" }`, and `resolveLenses(spec)` fills in its label and summary. Setting `label` or `summary` yourself overrides the preset. Lenses may cover only some nodes.
  - Well-Architected: `operational-excellence`, `security`, `reliability`, `performance`, `cost`, `sustainability`.
  - `network` ("Network"): ingress and egress paths, ports, protocols, NAT and firewalls. Pairs with the `traffic` tag.
  - `risks` ("Risks & trade-offs"): holds the outputs of an ATAM-style review, not the review. Start the badge with the kind and map it to a level: Risk is `risk`, Sensitivity point and Trade-off point are `warn`, Non-risk is `good`.
- Use `operational-excellence` for deploy and observability facts on tooling nodes. `flow` is built in and cannot be declared; duplicate lens ids are errors.

## Validator

Errors (spec will not render): bad version/title, duplicate ids, two nodes in one cell, unknown link or trace node, self-links, malformed waypoints or zone bounds, undeclared lens (on nodes or links), unknown `pattern`, `interaction` or `level`, a custom lens without a label, duplicate or reserved lens ids, a bad `scale` (needs 0 <= min <= max), unknown zone `kind`, member, or parent, a node in two zones, a zone parent cycle, a zone with nothing to size from, unreachable trace hop.

Mentions (confirmed): prose blocks, node details and links tag the node ids their text talks about. Unknown ids are errors. A node whose text describes another node it is not linked to is a warning, and when `prose` exists, a node that no prose block mentions is a warning. That is the "every described component has a node" check from the portfolio session.

Zone warnings: a node whose card overlaps a zone's drawn area without being a member, and two zones that overlap without being nested.

Traffic warnings: a link that crosses a `vpc` or `boundary` zone edge without a `traffic` tag, or tagged the wrong way. Unknown `traffic` values are errors.

Link warnings: `event`/`message`/`stream`/`batch` explicitly set to `sync`, `interaction` or `twoWay` set on a `dependency`, `twoWay` on an `event`.

Warnings (completeness lint): node without `detail` or without role/why, arrow without `detail`, grouped icons without captions, orphan node with no links, node never visited by the trace.

## Resolved

- **Coverage**: per-node `mentions` (above).

## Still open
